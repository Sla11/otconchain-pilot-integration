# Contributing

Propose a focused change with its reason, affected contract version and validation. Keep partner/client identities, internal endpoints, tickets, credentials, RFQ history and actual pilot evidence out of public issues and commits. Use synthetic examples.

For API changes, update the contract, fixtures, corresponding guide and acceptance cases together. Preserve native signed types unless a separately reviewed protocol change is intended. Mark breaking changes with a new version.

Run `npm ci`, `npm test` and `npm run client:dry-run`. Update diagram source and SVG exports together where relevant. Diagrams summarize the written contract; they do not override it.

No contribution is evidence of a partnership or operational acceptance. Discuss licensing with the repository owner before contributing material that requires a new license grant.
